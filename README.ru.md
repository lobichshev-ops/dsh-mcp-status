# dsh-mcp-status

Плагин для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness): кнопка **MCP** в шапке чата. Нажал — видно, какие MCP-серверы подключены к DSH и какие из них отвечают прямо сейчас, с числом доступных инструментов у каждого.

![Панель статусов MCP](docs/preview.png)

*На скриншоте — вымышленные серверы, не реальная конфигурация.*

## Зачем

DSH подключает MCP-серверы один раз, при старте. Когда сервер лежит, это видно косвенно: в наборе инструментов модели просто нет его инструментов, либо вызов падает с транспортной ошибкой. Конфиг говорит, что *должно* быть подключено, но не что подключено.

Порт, который кто-то слушает, — ещё не живой MCP-сервер: он может принимать соединение и не отвечать по протоколу. Плагин проверяет строже: **проходит ли сервер `initialize` + `tools/list` именно сейчас и сколько инструментов он вернул.** Это ровно то, что нужно самому Harness, чтобы дать модели эти инструменты.

## Что видно

- Пилюля в шапке чата с точкой состояния: зелёная — всё отвечает, красная — что-то мертво.
- Панель со списком серверов из конфига профиля: имя, транспорт, эндпоинт, состояние, время ответа, число инструментов.
- Отдельный блок инстансов `1C:EDT`, найденных по `.mcp.json` в папках проектов.
- Кнопка «Обновить». Ответ кэшируется, поэтому панель открывается мгновенно, хотя полная проверка идёт ~15 секунд.

## Как устроено

Две половины в одном пакете — обычная форма плагина с интерфейсом.

**Хост (`index.js`).** Объявляет `export const inject = ['webServer']`, в `ctx.effect` регистрирует маршрут `GET /plugin/mcp-status`, при старте и далее раз в 5 минут запускает проверку. Проверку делает дочерний процесс Python (`scripts/mcp_status.py`, только стандартная библиотека), который пишет результат в файл; плагин читает файл, кэширует JSON и раздаёт его.

**Клиент (`client.js`).** Классический скрипт, который регистрируется через `window.__ModuleLoader__.load` и экспортирует `{ inject: ['slots'], apply(ctx) }`. В `apply` он кладёт React-компонент в слот `conversation.session.header.utilities` — ту же полосу, где кнопки локали и Markdown. Компонент опрашивает маршрут при монтировании и далее раз в 20 секунд; пока хост сообщает `refreshing: true`, опрос идёт каждые 1,5 секунды, чтобы время в панели менялось сразу по готовности результата, а не через полминуты.

### Почему проверка не на JavaScript

Проверка — не пинг порта. Для каждого сервера по-настоящему выполняется MCP-хендшейк:

1. `POST initialize` с `Accept: application/json, text/event-stream`, с переходом по `307`-редиректу (`/mcp` → `/mcp/`).
2. Запоминается `Mcp-Session-Id`, отправляется `notifications/initialized` — без него часть серверов на FastMCP отвечает на `tools/list` ошибкой *Invalid request parameters*.
3. `POST tools/list` с этим заголовком; ответ разбирается и как обычный JSON, и как SSE-поток (`data: {...}`).
4. Для `stdio`-серверов — запуск команды и обмен JSON-RPC по stdin/stdout, причём с отдельными таймаутами на этапы: роутеру нужно ~12 секунд на `tools/list`, потому что он заново обходит диапазон портов.

Эта логика уже существует в виде проверенного Python-скрипта, поэтому хост-часть его переиспользует: второй источник истины на JavaScript только разошёлся бы с первым. Скрипт включён в пакет — внешних зависимостей нет.

Вывод дочернего процесса намеренно **не** забирается через pipe: скрипт пишет результат в файл (`--out`), плагин читает и удаляет его. Pipes ломаются в песочницах, а файл работает везде.

### Формат ответа

`GET /plugin/mcp-status` отдаёт конверт с кэшем:

```json
{
  "ok": true,
  "fetchedAt": 1793269934399,
  "durationMs": 14984,
  "refreshing": false,
  "error": null,
  "data": {
    "servers": [ { "name": "1c-edt", "transport": "stdio", "endpoint": "…", "state": "ok", "ms": 12293, "tools": 52, "detail": "" } ],
    "commentedOut": ["mcp-1c-metadata"],
    "edt": [ { "project": "Мой проект", "url": "http://127.0.0.1:8771/mcp", "state": "ok", "tools": 50 } ],
    "orphanPorts": []
  }
}
```

`?refresh=1` запускает проверку в фоне и сразу возвращает старый кэш с `refreshing: true`.

### Состояния

| Состояние | Значение |
| --- | --- |
| `ok` | Хендшейк прошёл; `tools` — сколько инструментов вернул сервер. |
| `warn` | `initialize` прошёл, `tools/list` — нет: процесс живой, но сломан. Причина в `detail`. |
| `dead` | Отказ соединения, таймаут, HTTP-ошибка или ответ не по протоколу. |
| `off` | В конфиге стоит `disabled: true`. |
| `skipped` | Не проверялся. |

## Настройка

Ключи необязательные, задаются в строке загрузчика:

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `pythonPath` | Python из рантайма DSH | Интерпретатор для скрипта проверки. |
| `scriptPath` | `scripts/mcp_status.py` в пакете | Свой скрипт, если нужно изменить проверку. |
| `intervalMs` | `300000` (5 минут) | Период фонового обновления, не чаще 15 секунд. |

Переопределение — в `cordis.patch.yml` профиля:

```yaml
- insert:
    - id: mcp-status
      name: '@local/dsh-mcp-status'
      config:
        intervalMs: 60000
```

### Скрипт проверки

scripts/mcp_status.py работает и сам по себе, без интерфейса:

`ash
python scripts/mcp_status.py                 # таблица для человека
python scripts/mcp_status.py --json          # машинный вывод
python scripts/mcp_status.py --json --out result.json   # записать в файл
python scripts/mcp_status.py --no-edt        # без блока 1C:EDT
python scripts/mcp_status.py --edt-roots 'D:\projects'  # каталоги EDT, если роутер их не передал
`

Код возврата: 1 — есть мёртвые серверы,   — все живы. Удобно для cron.

## Установка

1. Положить каталог в постоянное место и связать с профилем:

   ```powershell
   cd ~\.dsh\profiles\desktop
   pnpm add "link:<абсолютный путь к пакету>"
   ```

2. Добавить имя в список бандлов в `~/.dsh/profiles/desktop/package.json`:

   ```json
   "dsh": { "profile": { "bundles": [ "...", "@local/dsh-mcp-status" ] } }
   ```

3. Перезапустить DSH. Хост-часть поднимается вместе с профилем, клиентская появляется после перезагрузки страницы.

Удаление: убрать имя из `bundles` и выполнить `pnpm install`.

Имя `@local/dsh-mcp-status` произвольное — пакет приватный и в npm не публикуется. Меняйте его в `package.json`, `cordis.patch.yml`, а также в зависимостях и списке бандлов профиля.

## Если что-то не так

| Симптом | Причина |
| --- | --- |
| Кнопки нет | Клиентская половина регистрируется при загрузке страницы — обнови страницу (F5), не только приложение. |
| Маршрут отдаёт 404 | Хост-часть не активировалась: смотри stderr DSH на строки `[mcp-status]`, проверь строку загрузчика и резолв пакета из профиля. |
| `cannot get property "webServer" without inject` | Cordis запрещает читать сервис без объявления — в плагине есть `export const inject = ['webServer']`. |
| «Проверяю…» висит ~15 с | Так и должно быть: stdio-роутер каждый раз обходит порты. Только HTTP-серверы отвечают за ~200 мс. |
| `МЁРТВ` у проектов EDT | Инстанс EDT не запущен; в `.mcp.json` остался порт с прошлого запуска — это не ошибка. |

При импорте модуля и при ошибке `apply` в каталог пакета дописывается `.activation.log` (в git не попадает).

## Ограничения

- Маршрут зарегистрирован напрямую на веб-сервере, а не через аутентифицированный `/api`. Наружу отдаются только имена серверов, эндпоинты и состояния, но при публикации DSH на не-loopback адрес маршрут тоже станет доступен.
- Блок EDT специфичен для 1С; в других конфигурациях он просто ничего не находит.
- Клиентская половина не получает конфиг (DSH создаёт клиентские записи без него), поэтому все настройки живут в строке загрузчика.
